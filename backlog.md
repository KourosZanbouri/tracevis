| 2.2 | ~~Multi-RIPE-probe + IODA status cross-check~~ **DONE** | A single vantage point cannot reproduce allowlist asymmetry — that needs distributed probes. `--vps` downloads the same measurement from N RIPE Atlas probes and renders them in one combined graph with per-VP colour-coded edges (reusing the existing `REQUEST_COLORS[measurement_steps]` cycle). `--ioda-country IR` (default) cross-checks IODA v3 outage data and annotates VPs whose source is in an active-outage country. | 2.12 | ~~Detect on-path interception from the reply itself~~ **DONE (M7)** | Addressing a probe to a chosen resolver guarantees the destination *field*, not the destination, and nothing in the outgoing packet can prevent an on-path box answering in its place — but the reply has to come back, and it carries evidence. Two signals, either sufficient: **IP-ID reflection** (the reply keeps the query's IP ID, so the box mutated the request rather than composing an answer; ~1-in-65536 per probe by chance) and **TTL implausibility** (the reply implies an initial TTL no real stack emits). DF was dropped as a signal: genuine replies lack it too. | M | 2.0 |
| 2.10 | **PARTIAL** — `--compare-arms` extracts what the captures already prove; a controlled endpoint is still needed for the UDP arm | The original framing was too pessimistic. It is right that a controlled endpoint would settle everything, but wrong that the captures say nothing without one, and re-reading them turned up more than the item claimed. **grpc-h2c / shadowsocks:** the control reaches `1.1.1.1` at hop 10/9 with a `PSH-ACK` carrying payload, while the treatment — same path, same port, same destination, first three hops identical — gets nothing across 20 hops. That is a payload-dependent difference, and the verdict is *probably dropped on path* rather than a certainty only because these captures do not record whether the treatment's **handshake** reached the destination. **wireguard:** both arms die at hop 3 on every destination, so the block is not payload-based at all — it is the port or the path, which is a result and not a failure to measure. **The blocker was misidentified.** The handshake runs to the destination without a TTL limit, so a SYN-ACK proves reachability and separates "dropped on path" from "never reachable" — and only handshake *failure* was ever recorded, as free text. It is now recorded per hop as `handshake`, so a re-run settles the two TCP samples with no new endpoint at all. An endpoint is still genuinely required for the UDP arm, where silence from a closed port is indistinguishable from an on-path drop. | M | 2.5 |
| 2.11 | ~~Derive `cgnat_hop` from per-hop evidence, not from `network_state` alone~~ **DONE (M5f)** | `cgnat_hop` was derived from `network_state` alone, so it could not fire on a network the detector had already mis-classified — including ones whose traces crossed an obvious RFC 6598 hop. The semantics question resolved the other way than expected: `dpi_cleared`'s `not cgnat_hop` clause turned out to be **inert** (`cgnat_hop` implied `allowlisted`, `dpi_cleared` requires `open`), so dropping it changed nothing and stopped the new evidence from raising a false alarm on every uncensored CGNAT carrier. | M | 1.9 |

## §4 — Adapting to network changes since Aug 2026

Sources and evidence: the Oct 2026 addendum (§15) of
`IRAN_INTERNET_CIRCUMVENTION_REPORT.md`. Every live-network item keeps the
§1.4 discipline: build, test offline against scapy/`FakeNetwork`, and cap
verdicts at *moderate* until a censoring path has confirmed them.

| ID | Pri | Task | Why | Risk | Depends on |

| 4.1 | P1 | **Record ICMP type/code per hop** | `parse_packet` keeps only scapy's `summary()` string. Administratively-prohibited unreachables (3/9, 3/10, 3/13) are how an allowlist *rejects*, as distinct from silently dropping (`tcp_silently_dropped`) or TTL expiry.
